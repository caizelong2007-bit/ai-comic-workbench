# 短剧连续性状态层与变体资产方案

## 背景

短剧生产并不是简单的：

```text
剧本 -> 分镜 -> 资产 -> 提示词包 -> 视频
```

在真实生产中，很多问题来自“连续性状态”没有被系统显式保存。例如：

```text
Benson 已经穿上盔甲。
故事发生在大地图中，但当前镜头实际是在铁匠铺侧面的碎石草丛。
龙蛋被 Benson 左臂护住，而不是放在地上。
铁匠铺的门上一镜已经被撞开。
小龙蜥目前只是警惕靠近，还没有完全信任 Benson。
```

如果这些状态没有结构化保存，下游每一步都只能让 LLM 从文本中重新猜。这样会导致角色状态、场景位置、道具归属、关系进展不稳定。

推荐的底层方案不是单纯依赖提示词，也不是为每一个动作都生成新资产，而是采用混合结构：

```text
基础资产 + 连续性状态层 + 变体资产
```

## 核心原则

整个管线遵循一个原则：

```text
默认继承，事件改变。
```

也就是说：

- Benson 一旦穿上盔甲，后续镜头默认继承装备状态，直到剧本明确写他脱下、换装、盔甲损坏。
- 角色进入铁匠铺后，连续镜头默认仍在铁匠铺或其局部区域，直到剧本明确离开或发生场景切换。
- 门被撞开后，后续镜头中门应保持被撞开的状态。
- 小龙蜥如果上一镜只是警惕，下一镜不能突然完全忠诚，除非中间有建立信任的剧情事件。

LLM 可以负责提出状态变化，但不应该让 LLM 每次都重新猜状态。后端需要保存、继承、校验这些状态，并把它们暴露给前端和提示词生成模块。

## 三类资产与状态

### 基础资产

基础资产表示一个实体的稳定身份。

例子：

```text
CHAR01 Benson
LOC01 三国边境大世界
PROP01 紫色龙蛋
```

基础资产回答的是：

```text
这个东西是谁/是什么？
默认形态长什么样？
项目内如何保持它的身份一致？
```

### 变体资产

变体资产表示同一个实体在持续状态下的另一种稳定形态。

例子：

```text
CHAR01-V01 Benson 新手套装形态
CHAR01-V02 Benson 受伤装备形态
LOC04-V01 门被撞开后的废弃铁匠铺
PROP01-V01 出现裂纹的紫色龙蛋
```

变体资产回答的是：

```text
同一个实体发生持续视觉变化后长什么样？
这个形态是否会在多个分镜或多集里复用？
```

对于视频生成来说，变体资产非常重要。视频模型通常更容易理解一张完整的“穿盔甲 Benson”参考图，而不是自己根据“Benson + 盔甲 + 提示词”去组合。

### 临时状态

临时状态表示当前镜头中的动作、情绪、持物、姿态、关系等，不一定要生成新资产。

例子：

```text
Benson 手持剑
Benson 抱着龙蛋
Benson 警惕
Benson 蹲下
龙蛋强烈发光
空气中有灰尘
小龙蜥谨慎靠近
```

这些内容应该进入连续性状态层和提示词包，而不是都变成新资产。

## 什么时候需要生成变体资产

建议生成变体资产的情况：

- 换装、穿盔甲、戴面具、披斗篷。
- 变身、升级、黑化、觉醒、伪装。
- 会持续多个镜头的受伤、污染、破损。
- 角色年龄、形态、体型发生变化。
- 重要场景发生持续性破坏或重构。
- 核心道具出现持续性状态变化，例如龙蛋裂开、核心启动、盒子打开。

不建议生成变体资产的情况：

- 单次动作：奔跑、转身、举手、摔倒。
- 普通情绪：害怕、愤怒、惊讶。
- 短暂环境效果：火光、烟雾、雨水、灰尘。
- 短暂持物：临时拿一下剑、递食物。
- 运镜和角度。
- 临时背景杂物。

判断标准：

```text
如果这个状态会持续影响多个镜头的视觉一致性，就考虑生成变体。
如果它只描述当前镜头动作，就放在分镜状态里。
```

## 角色变体的生成方式

以“Benson 穿新手套装”为例，推荐流程是：

```text
Benson 基础参考图
+ 新手套装参考图
+ 项目风格参考图
+ 变体生成提示词
-> 生成 Benson 新手套装形态参考图
-> 用户审核
-> 审核通过后成为后续装备状态下的优先角色资产
```

建议保存结构：

```json
{
  "id": "CHAR01-V01",
  "type": "character_variant",
  "name": "Benson 新手套装形态",
  "parentAssetId": "CHAR01",
  "appliedAssetIds": ["PROP05"],
  "stateKey": "armored",
  "status": "approved",
  "prompt": "Benson 穿着新手战士护甲，保留 Benson 的脸型、发型、方块身体比例、少年感和项目体素风格。",
  "imageUrl": "/cache/images/char01-v01.png",
  "createdFrom": {
    "baseAssetId": "CHAR01",
    "stateAssetIds": ["PROP05"],
    "sourceShotId": "SH02"
  }
}
```

变体必须保留基础角色身份，不能因为穿了装备就把 Benson 重新设计成另一个人。

## 连续性状态层

连续性状态层负责连接：

```text
资产 -> 分镜 -> 提示词包 -> 视频请求
```

它保存的是“当前镜头中什么状态是真的”，而不仅是“当前镜头引用了哪些资产”。

建议的分镜状态结构：

```json
{
  "shotId": "SH02",
  "state": {
    "characters": [
      {
        "assetId": "CHAR01",
        "activeVariantId": "CHAR01-V01",
        "wearing": ["PROP05"],
        "holding": ["PROP06"],
        "carrying": [
          {
            "assetId": "PROP01",
            "position": "left arm"
          }
        ],
        "emotion": "cautious",
        "pose": "lowering sword tip",
        "injury": "",
        "trustState": {
          "CHAR04": "not yet trusted"
        }
      }
    ],
    "location": {
      "primaryAssetId": "LOC04",
      "parentAssetIds": ["LOC01"],
      "zone": "铁匠铺侧面的碎石草丛",
      "damageState": "木门已经被撞开"
    },
    "props": [
      {
        "assetId": "PROP01",
        "ownerAssetId": "CHAR01",
        "position": "左臂护住",
        "state": "完整，正在发出紫色脉冲光"
      }
    ],
    "relations": [
      {
        "fromAssetId": "CHAR01",
        "toAssetId": "CHAR04",
        "type": "trust",
        "state": "正在建立信任，但仍然警惕"
      }
    ],
    "continuity": {
      "fromPrevious": "Benson 被逼到侧面后恢复平衡。",
      "toNext": "小龙蜥迟疑靠近食物，但战场噪声变强。"
    }
  }
}
```

## 需要处理的典型问题

### 角色状态

常见状态：

- 穿着盔甲、校服、外套、头盔、面具。
- 手持剑、抱着龙蛋、背着包。
- 受伤、疲惫、湿透、中毒、昏迷、被绑。
- 变身、升级、黑化、伪装。
- 情绪：警惕、愤怒、恐惧、信任、怀疑。
- 位置：门外、屋内、墙后、车上、坑底。

处理方式：

- 持续外观变化：生成或建议生成变体资产。
- 临时动作和情绪：保存为分镜状态。
- 提示词生成时要表达关系：

```text
@Benson 新手套装形态 右手放低 @新锻造的剑，左臂护住 @紫色龙蛋。
```

避免变成：

```text
@Benson、@新手套装、@新锻造的剑、@紫色龙蛋 同时出现。
```

### 场景层级

常见层级：

```text
大世界 -> 矿山入口 -> 铁匠铺 -> 铁匠铺侧面草丛
城市 -> 学校 -> 教室 -> 窗边座位
城堡 -> 王座厅 -> 断裂楼梯
```

处理方式：

- 分开保存父级场景和当前主场景。
- 当前镜头优先使用最具体的场景资产。
- 大地图/大世界资产用于地理关系和风格，不应默认替代局部场景。
- 只有远景、航拍、转场、旅行、缺少局部场景资产时，才优先使用大地图资产。

### 场景状态

常见状态：

- 门已经打开或被撞坏。
- 屋顶坍塌。
- 熔炉已点燃。
- 桥断裂。
- 房间进水。
- 陷阱已经触发。

处理方式：

- 持续影响多个镜头的场景变化，可以生成场景变体。
- 短暂氛围留在状态文本中。
- 提示词包必须描述会影响当前画面的场景状态。

### 道具归属和位置

常见状态：

- 龙蛋在 Benson 左臂。
- 剑在右手，剑尖放低。
- 钥匙在背包里。
- 地图摊在桌上。
- 手机屏幕裂开。

处理方式：

- 道具不能只用 `assetRefs` 表示。
- 需要保存 owner、position、state。
- 提示词生成时必须写清楚道具归属和位置。

### 关系状态

常见关系：

- 小龙蜥仍然警惕，还没完全信任 Benson。
- 敌人已经发现 Benson。
- Boss 知道 Benson 的存在，但还没现身。
- 两个角色失散。
- 某角色假装合作。

处理方式：

- 保存关系类型和当前阶段。
- 关系变化应作为事件记录。
- 后续镜头不能跳过必要的信任建立、背叛、发现、反应过程。

### 剪辑承接状态

常见问题：

- 上一镜 Benson 摔倒，下一镜不能直接开始挖矿。
- 上一镜揭示紫光，下一镜应先有发现或反应。
- 如果发生时间跳切，需要说明省略了什么，以及现在是什么状态。

处理方式：

- 保留 `entryBeat / mainBeat / exitBeat / cutRelation / ellipsis`。
- 下一镜默认继承上一镜的 `exitBeat` 状态。
- 如果跳切，必须有明确的 `ellipsis` 和新状态说明。

## 与生产管线的配合

### 1. 分集剧本阶段

分集剧本需要识别会持续影响后续镜头的事件：

```text
Benson 穿上盔甲。
龙蛋开始持续发光。
铁匠铺木门被撞开。
小龙蜥开始信任 Benson。
```

LLM 负责：

- 提出状态事件。
- 判断哪些变化是持续性的。
- 给出变体候选建议。

后端负责：

- 保存事件。
- 记录事件发生的剧集和分镜顺序。
- 避免重复事件和冲突事件。

### 2. 分镜脚本生成阶段

分镜脚本不只要写动作，还应输出状态变化提示。

建议字段：

```json
{
  "stateIn": {
    "CHAR01": "穿着新手套装，护着龙蛋，手持剑",
    "LOC04": "木门已被撞开，侧面碎石可见"
  },
  "stateChange": [
    {
      "entityId": "CHAR04",
      "change": "开始靠近食物，但仍然警惕"
    }
  ],
  "stateOut": {
    "CHAR04": "迟疑靠近食物"
  }
}
```

LLM 负责：

- 从剧情中推断状态变化。
- 说明本镜头改变了什么。

后端负责：

- 与上一镜状态合并。
- 检查是否出现不合理跳跃。
- 必要时要求重试或提示用户确认。

### 3. 资产提取阶段

资产提取不应只选择资产，还应说明资产在本镜头中的状态关系。

示例：

```json
{
  "shotId": "SH02",
  "selectedAssets": [
    {
      "assetId": "CHAR01-V01",
      "role": "当前主角变体",
      "reason": "Benson 当前为装备状态"
    },
    {
      "assetId": "PROP06",
      "role": "手持道具",
      "ownerAssetId": "CHAR01",
      "relation": "右手持剑，剑尖放低"
    }
  ],
  "variantCandidates": [
    {
      "parentAssetId": "CHAR01",
      "appliedAssetIds": ["PROP05"],
      "reason": "盔甲状态会持续多个镜头"
    }
  ]
}
```

LLM 负责：

- 识别视觉上重要且持续的状态变化。
- 建议是否需要变体。
- 选择影响一致性的关键资产。

后端负责：

- `shot.assetRefs` 仍作为当前镜头参考资产列表。
- 状态关系另存，不混进普通资产列表。
- 状态或资产变化后，标记旧提示词包和旧视频过期。

### 4. 变体资产生成阶段

变体生成应是一个可控步骤，不应在后台悄悄发生。

推荐交互：

```text
系统检测到：Benson 在多个分镜中处于装备状态。
建议生成变体：Benson 新手套装形态。
用户可以选择：生成参考图 / 上传参考图 / 暂时跳过 / 合并为普通状态。
审核通过后，后续相关镜头默认使用该变体。
```

为什么要用户审核：

- 主角变体会影响很多后续镜头。
- 错误变体比缺少道具更容易破坏连续性。
- 用户只需要对关键变体确认一次，后续可以自动复用。

### 5. 提示词包生成阶段

提示词包生成输入应包括：

```text
分镜脚本
shot.assetRefs
连续性状态
当前激活的变体资产
项目风格
视频模型 profile
```

输出时应把状态编译成自然的模型指令：

```text
@Benson 新手套装形态 右手放低 @新锻造的剑，左臂护住 @紫色龙蛋，站在 @废弃铁匠铺 侧面的碎石草丛旁。
```

后端需要校验：

- 提示词包不能引用 `shot.assetRefs` 之外的资产。
- 如果当前状态有已审核变体，应优先使用变体，而不是基础角色 + 装备道具。
- 如果状态在提示词包生成后变化，提示词包必须标记过期。

### 6. 视频生成阶段

视频请求仍保持现有结构：

```text
prompt = 编译后的分镜提示词
image_urls = 当前分镜资产和变体资产的参考图
```

规则：

- 当前变体应替代基础资产成为主要角色参考。
- 临时手持道具如果重要，可以作为独立参考图。
- 父级/大地图场景不能替代当前具体场景。
- 如果关键变体没有参考图，应在生成视频前提示用户。

## 模型、后端、用户的职责边界

### LLM 适合负责

- 判断剧情事件是否改变了持续状态。
- 判断角色形态是否发生明显变化。
- 判断当前镜头哪些状态重要。
- 判断哪些资产需要作为视觉参考。
- 把状态关系写成自然、可执行的视频提示词。

### 后端必须负责

- 状态继承。
- 分镜顺序和事件顺序。
- 资产 ID 有效性。
- 变体和基础资产的父子关系。
- 状态变化后标记提示词包过期。
- 提示词包变化后标记视频过期。
- 参考图数量限制和模型规则。
- 禁止提示词包凭空引用不存在的资产。

### 用户需要审核

- 主角变体。
- 重要服装、盔甲、变身、升级形态。
- 重要场景破坏后的变体。
- 核心道具状态变体。
- 会影响多个后续镜头的参考图。

## 前端需要的能力

### 分镜状态面板

在分镜编辑页或分镜详情中展示：

```text
当前角色状态
当前场景状态
当前道具归属
从上一镜继承了什么
本镜改变了什么
状态冲突或缺失提醒
```

### 变体建议面板

当系统检测到持续状态时展示：

```text
建议生成变体：Benson 新手套装形态
原因：Benson 在 4 个分镜中持续穿着新手套装
操作：生成参考图 / 上传参考图 / 暂时跳过 / 合并为普通状态
```

### 提示词预览

展示状态如何被编译进最终提示词：

```text
@Benson 新手套装形态 左臂护住 @紫色龙蛋，右手放低 @新锻造的剑。
```

这样用户能看出来系统到底是把盔甲理解成“穿在 Benson 身上”，还是只是把盔甲当成一个独立物体。

## 验收标准

1. 角色穿上盔甲后，后续分镜默认继承装备状态，直到剧情改变。
2. 如果已审核的装备变体存在，后续提示词优先使用变体，而不是基础角色 + 盔甲道具。
3. 如果没有变体，提示词也必须写成“Benson 穿着盔甲”，不能只是平铺资产列表。
4. 当前具体场景优先级高于父级大地图场景。
5. 持续的场景破坏可以生成场景变体。
6. 重要道具需要记录 owner 和 position。
7. 提示词包必须把状态关系编译成自然语言。
8. 关键变体或关键参考图缺失时，视频生成前需要提示。
9. 主角变体成为默认资产前，需要用户确认。
10. 不改变现有视频 API 请求字段结构，只改变内部状态管理和提示词编译逻辑。

## 初期不做的内容

- 不自动批准所有变体。
- 不为每一个姿势或情绪生成变体。
- 不做完整物理模拟或空间模拟。
- 不替代现有资产库。
- 不改变 Seedance/APIMart 请求字段。

## 推荐落地阶段

### 第一阶段：状态文档与展示

- 增加连续性状态 schema。
- 在分镜编辑中展示状态。
- 让用户能看到继承状态和本镜变化。

### 第二阶段：提示词编译

- 提示词包生成时读取状态。
- 将穿戴、持有、携带、场景层级、道具归属编译成自然提示词。
- 保持现有视频 API payload 不变。

### 第三阶段：变体候选检测

- 检测持续的角色、场景、道具变化。
- 向用户展示变体建议。
- 主角变体不自动生成、不自动启用。

### 第四阶段：变体资产生成

- 用基础资产 + 应用资产 + 项目风格生成变体参考图。
- 保存父子关系。
- 增加审核流程。

### 第五阶段：校验与提醒

- 状态和资产冲突时提醒。
- 提示词包忽略当前状态时提醒。
- 视频早于最新状态或提示词时提醒。
